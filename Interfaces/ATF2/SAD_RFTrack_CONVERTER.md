# Unified ATF SAD → RFTrack converter

`convert_atf_sad_to_rftrack.py` is the common front door for a SAD daihon.  It
uses the same SAD parser and emits the same two artifacts for every region:

- `atf_<daihon-name>_sad_lattice.json`: authoritative, auditable structural export;
- `atf_<daihon-name>_sad_lattice.tfs`: static magnetic/RF TFS exchange input.

Convert a daihon with no accelerator-specific interpretation option:

```bash
python convert_atf_sad_to_rftrack.py \
  --sad /path/to/daihon.sad --output-dir /tmp/export
```

The strength convention is always the SAD manual convention: `K0`, `K1`,
`K2`, ... are integrated field components, and a BEND face angle is
`E1 * ANGLE + AE1` (or `E2 * ANGLE + AE2`).

For the four archived ATF daihons, the source path automatically supplies only
the usual route name and reference momentum: Linac → `linac`, BT → `bt`, DR →
`RING0`, Ext → `ATF2`.  `ATF2` is simply the name of the extraction/final-focus
LINE declared inside that particular daihon; it is not a user option or a
physics setting.

For a different daihon with exactly one LINE, that LINE is selected
automatically.  If it has multiple LINEs, conversion stops and prints their
names: only then must the user identify the intended physical route, for
example:

```bash
python convert_atf_sad_to_rftrack.py \
  --sad /path/to/daihon.sad --line INJECT_TO_RING --output-dir /tmp/export
```

The TFS is a direct source translation, not a SAD Twiss solution.  In
particular, Linac tracking must still use `prepare_accelerating_lattice()` to
replace the generic imported RF cavities by travelling-wave structures and
retune magnets for the energy profile.  DR periodic Twiss must still be
generated by linearising the built RFTrack ring about its closed orbit.

This converter is the common *source-of-lattice* layer; it does not silently
replace the existing specialised tracking models.  The DR builder adds thin
skew/roll companions for correction studies, and the legacy Ext TFS is a
MAD-X-derived model.  Compare the exported element-by-element field data and
the relevant orbit/optics observables before switching either runtime model to
the direct SAD export.

## Component coverage and source conventions

The coverage table was checked against the official [SAD/FFS command
reference](https://acc-physics.kek.jp/SAD/how-to-use-sad/sad-ffs-command-sad-script/)
and the [RF-Track reference manual](https://gitlab.cern.ch/rf-track/rf-track-reference-manual/-/raw/master/RF_Track_reference_manual.pdf?ref_type=heads).
The JSON manifest is authoritative: it retains source attributes and the
per-element `mapping_status`.  It records the input file name and SHA-256
digest, rather than the sender's local absolute path.  Unknown SAD element
declarations are a hard error; they are never silently treated as drifts.

| SAD component | JSON / native RFTrack mapping | TFS mapping | qualification |
|---|---|---|---|
| `DRIFT` | `Drift` | `DRIFT` | direct |
| `BEND` | `SBend`, with SAD face rule `E1*ANGLE+AE1` | `SBEND` | direct magnetic geometry; SAD-specific fringe/coordinate maps still need comparison |
| corrector-style `BEND` (`ZH/ZX`, `ZV/ZY`) | `Corrector`, with SAD `K0` as the kick in radians | `HKICKER` / `VKICKER` | powered case uses the native builder; TFS export is fail-closed |
| `QUAD`, `SEXT` | `Quadrupole`, `Sextupole` | corresponding TFS types | direct SAD integrated `K1/K2` convention |
| `OCT`, `DECA`, `DODECA`, `MULT` | `Multipole` using normal and skew `KnL` | `MULTIPOLE`, `K0L…K20L`/skew columns | native builder covers SAD `K0…K21`, `SK0…SK21`; RF-Track TFS import is fail-closed for nonzero order 21 |
| `SOL` | `Solenoid(L, BZ, RADIUS)` | `SOLENOID` | isolated field is direct; SAD overlap/boundary geometry is explicitly flagged |
| `CAVI` / `CAV` | disabled drift by default; finite-length Linac CAVI can become `TW_Structure` | `RFCAVITY` | RF synchronisation and beam loading remain model-specific |
| `TCAVI` | retained but requires an external calibrated RF field model | field-free `MARKER` | intentionally not approximated as a transverse kick |
| `MONI`, `MARK` | `Bpm`, zero-length `Drift` | `MONITOR`, `MARKER` | direct |
| `COORD` | source parameters retained | `MARKER` | no one-to-one RFTrack lattice map; status is explicit |
| `APERT` | source boundary parameters retained | `MARKER` | explicit RF-Track aperture geometry must be selected; no silent rectangular/elliptical assumption |
| `DX`, `DY`, `ROTATE` on supported elements | post-placement RFTrack offsets | source retained / `TILT` | validated for API placement; field-roll convention still needs SAD-map comparison |

`RADIUS` is retained but is not automatically converted to a machine aperture:
in SAD it also controls space-charge/aperture semantics, so an engineering
aperture model must state its own geometry and loss policy.

SAD `LINE` repetition (`n*element`) is expanded.  Reverse traversal
(`-element` or `-line`) is deliberately rejected: it needs an inverse map with
validated bend, RF and coordinate conventions, rather than a silent sign flip.

A zero-angle `BEND` with nonzero `K0` or `K1` is accepted as a corrector only
when its ATF name identifies its plane (`ZH`/`ZX` for horizontal, `ZV`/`ZY`
for vertical).  An otherwise ambiguous powered BEND is rejected instead of
being guessed as a horizontal corrector.
